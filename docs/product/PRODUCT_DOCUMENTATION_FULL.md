## One-sentence definition

A self-hosted platform that accepts a browser task such as â€œlog in, navigate, extract, fill, download, or verify,â€ executes it inside an isolated Chromium session, and returns structured results, artifacts, logs, and an auditable run history without requiring the browser workload to be hosted by a third-party SaaS.

This repository turns the idea into an ordered source of truth suitable for a human engineer or coding agent. ## Core product thesis

Do **not** build another generic Chromium hosting layer first. Existing products already cover major parts of that problem. The initial differentiation should be the self-hosted **agent execution + control plane**:

- natural-language goal â†’ browser actions â†’ structured result;
- local/private deployment;
- model-provider choice, including local models;
- reliable retries, cancellation, timeouts and resumability;
- persistent sessions when explicitly enabled;
- task history, screenshots, traces and audit events;
- pluggable browser backends: local Playwright first, optional remote/CDP backend later;
- Docker-first operations.

# V1 / V2 / V3 summary

## V1 â€” Self-hosted developer MVP

**Goal:** prove that a single operator can deploy the product and run reliable browser tasks without cloud browser infrastructure.

### Must have
- Docker Compose install.
- Web dashboard + public REST API.
- API key authentication.
- Create, inspect, cancel and retry runs.
- Input: start URL, natural-language goal, optional JSON output schema, max duration, model profile.
- Local Chromium via Playwright.
- Isolated browser context per ephemeral run.
- Basic persistent browser profile as an explicit opt-in capability.
- Agent loop with bounded steps and token/cost limits.
- OpenAI, Anthropic, Gemini and OpenAI-compatible endpoint adapters; local OpenAI-compatible servers supported.
- Actions: navigate, click, type, select, wait, scroll, upload, download, screenshot, extract.
- Structured JSON result with schema validation.
- PostgreSQL metadata.
- Redis/BullMQ job queue.
- Local filesystem or S3-compatible artifact storage.
- Screenshots, action log, console/network summary, final URL and error reason.
- Retry/backoff for infrastructure failures, not blind replay of unsafe side effects.
- Webhook on terminal run state.
- Domain allow/deny policy, private-network blocking by default, download limits and task timeouts.
- Health endpoints, structured logs, basic metrics.
- TypeScript SDK or generated API client.

### V1 non-goals
- residential proxies;
- automatic CAPTCHA solving;
- enterprise SSO;
- multi-region execution;
- full workflow DAGs;
- billing;
- managed SaaS control plane;
- extension marketplace;
- arbitrary untrusted third-party code execution;
- full TinyFish/Browserbase parity.

## V2 â€” Team and operations

**Goal:** make the system useful for an engineering/operations team, not only one developer.

Add:
- organizations/workspaces, RBAC and service accounts;
- encrypted credential vault and secret references;
- persistent profiles with explicit lifecycle controls;
- scheduled/recurring runs;
- human-in-the-loop approval checkpoints;
- reusable task templates and variables;
- run recording/live view;
- proxy provider adapter and optional remote browser/CDP backend;
- concurrency pools, quotas and priorities;
- richer webhooks, idempotency keys and delivery retries;
- OpenTelemetry traces + Prometheus metrics;
- admin controls, retention policies and audit export;
- Kubernetes/Helm deployment profile;
- stronger worker isolation and sandbox profiles;
- workflow chaining for a small number of sequential steps.

## V3 â€” Distributed platform

**Goal:** support enterprise and large distributed browser workloads.

Add:
- distributed worker/fleet registration;
- region-aware routing and autoscaling;
- policy engine for domain/network/action permissions;
- enterprise SSO/SAML/OIDC and SCIM;
- Vault/KMS secret integrations;
- multi-tenant hard isolation profiles;
- workflow DAGs and long-running resumable workflows;
- model routing by cost/latency/reliability;
- evaluation harness and task benchmark suites;
- browser image/version management and approved extensions;
- search/fetch fast path that avoids full browser sessions where possible;
- rich session replay and observability search;
- advanced data retention/legal hold controls;
- optional managed control-plane architecture while keeping workers self-hostable.

## Suggested calendar for one experienced developer using coding agents

- V1: 4â€“6 focused weeks.
- V2: +6â€“10 weeks.
- V3 foundation: +3â€“6 months.

These are planning ranges, not commitments. The biggest uncertainty is browser-agent reliability on diverse third-party websites, not CRUD implementation.

# Product brief

## Definition

A self-hosted browser-agent execution platform for developers and teams that need AI to interact with live websites while keeping browser sessions, credentials, artifacts and execution history under their control.

## Primary users

### P-001 â€” AI application developer
Needs a stable API to give an application browser capabilities without running Chromium lifecycle logic inside the app.

### P-002 â€” Internal automation engineer
Automates vendor portals, dashboards, form-heavy sites and workflows without reliable APIs.

### P-003 â€” Privacy/security-conscious company
Needs browser sessions and credentials to stay in its infrastructure.

### P-004 â€” Self-host operator
Needs Docker, backups, upgrades, logs, health checks, storage configuration and predictable failure modes.

## Core jobs to be done

- â€œGiven a goal and starting URL, complete the browser task and return structured output.â€
- â€œReuse a signed-in browser profile without exposing credentials to every caller.â€
- â€œSee exactly what the agent did and why a run failed.â€
- â€œRun the same automation repeatedly without babysitting browser infrastructure.â€
- â€œChoose my own model provider or local model endpoint.â€

## Constraints

- self-host-first;
- browser-first, not generic desktop automation;
- API-first with usable web console;
- TypeScript-first implementation;
- PostgreSQL + Redis + S3-compatible storage;
- no mandatory managed cloud dependency;
- no requirement to build proxy/CAPTCHA infrastructure in V1;
- auditable execution is a core requirement, not an add-on.

## Why this could fail

- existing open-source browser APIs already solve enough of the problem;
- browser agents remain unreliable on high-variance websites;
- maintenance burden from browser/website changes becomes too high;
- security expectations for credentialed automation exceed a small project's capacity;
- users prefer hosted convenience;
- local models may be too weak for reliable UI reasoning.

## Validation gate

Before V2, at least three real workflows should run repeatedly with acceptable success and recovery behavior, and at least two external users/operators should deploy the system without author intervention.
